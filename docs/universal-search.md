# Universal search fallback — never a dead end (2026-08-29)

## The real problem

The marketplace's own search box was a plain client-side name filter over the local `known_agents` cache — it only ever matched `${name} ${strategy}` substrings. If a user pasted a specific agent id, a wallet address, or a contract address, and it wasn't a name-text match (which it almost never would be — an id/address isn't a name), the result was a silently empty grid: no message, no explanation, no path forward. For a project whose whole stated point is transparency, that's exactly the wrong failure mode — the site should never leave a user guessing whether their input was wrong, whether the thing they searched for doesn't exist, or whether it exists but just isn't in this marketplace's own limited, curated view.

## What was actually checked, per input type

**Agent id.** A real, load-bearing finding, checked directly rather than assumed: `known_agents`'s own `_id` field is 8004scan's *internal listing UUID*, not the real, on-chain ERC-8004 `token_id` a user would actually see referenced anywhere else (BscScan, 8004scan's own pages, an on-chain job's provider metadata). They're stored as two separate fields. A user pasting a plain number almost certainly means the real token id — this was confirmed by checking `fetch_agent_detail()` (already built, `adapters/bsc.py`), which hits 8004scan's real, live `/api/v1/agents/{chain}/{id}` endpoint keyed by token id, not by their internal UUID. Live-verified against several real token ids, including one deliberately picked to be a genuine local cache-miss (present in the full, unfiltered registry scan but not yet promoted into `known_agents`) and one genuinely nonexistent id (confirmed, not just assumed, via a real 404 from 8004scan itself). A UUID-shaped query that misses locally is disclosed as unresolvable live — 8004scan's public API has no lookup path keyed by their own internal id, only by token id + chain, so there's honestly nothing further to check for that specific shape.

**Wallet (EOA).** A real, live `eth_getCode` check (empty result = no contract code = a real externally-owned account) distinguishes this from a contract, for free, via the same BSC RPC every other on-chain read in this project already uses. Real BNB balance (`eth_getBalance`) and real transaction count (`eth_getTransactionCount`) are both free, unlimited, single-call reads — live-verified against a real, well-known address (BNB's own public burn address) and a real registered agent's owner wallet.

**Contract — deliberately NOT a general-purpose identification engine.** Two real, live layers, in order: (1) a small, curated, hardcoded list of contracts already known to this specific project (its own AgenticCommerce/EvaluatorRouter/OptimisticPolicy/AgentAccessMarket contracts, plus PancakeSwap/Venus/Aave/Lista/WBNB/USDT — the exact same real addresses already hardcoded across the frontend's own Skills code, never independently re-sourced); (2) a live, on-chain ERC-20 self-check (`name()`/`symbol()`/`decimals()`/`totalSupply()`) for anything not on that list — live-verified against a real token deliberately NOT on the hardcoded list (PancakeSwap's own CAKE token), correctly self-identified via the live read alone. A contract that's neither a known address nor a real ERC-20 gets an honest "a real, live smart contract, genuinely unidentified" — never a guess, and explicitly not treated as a failure.

**Token.** Covered by the same ERC-20 self-check as "contract" above — a token IS a contract, and the live read gives real name/symbol/decimals/supply directly from the chain, not a third-party token list that could be stale or incomplete.

## Real, honest limitations found

- **No Zerion/full-portfolio enrichment for a plain wallet.** Zerion (`adapters/zerion.py`) has a real, tight 300/day quota shared with this project's existing opt-in wallet-portfolio feature. A universal search fallback could plausibly be hit far more often and by more varied addresses than that quota supports safely, so this deliberately uses only the free, unlimited RPC path (BNB balance + transaction count) — real and honest, but narrower than the full multi-token portfolio the existing opt-in panel shows for a specific agent's own owner wallet.
- **No general contract-source identification.** There's no live, free path in this project to a verified-source database for arbitrary BSC contracts (BscScan's own API needs a paid tier for BSC specifically — already investigated and confirmed in `core/rpc.py`'s own docstring for a different feature). A contract outside the curated list and outside plain ERC-20 shape is reported as genuinely unidentified, not guessed at.
- **BSC mainnet only**, matching this project's stated scope everywhere else — a token id fallback only checks chain 56, the same scope `adapters/bsc.py`'s `MAINNET_CHAIN_ID` already commits to.
- **A UUID-shaped miss can't be resolved live** — see above; disclosed plainly to the user rather than silently returning nothing.
- **What the 5-minute cache covers, and what it doesn't.** It protects against repeat searches of the *same* input burning quota — the real ask. It's not a general anti-scraping rate limiter (no per-IP request cap); a script hammering many *distinct* random addresses could still generate real RPC/8004scan load. Not built here — a genuinely different, larger piece of infrastructure (request-level rate limiting) than "cache repeat lookups," and this endpoint's real cost per call is cheap (a couple of free RPC reads, or a single 8004scan call only on a genuine local miss), not the kind of expensive operation that would make this an urgent gap today.

## What shipped

- `backend/core/universal_search.py` — `classify_query()` (address / uuid / token_id / unrecognized), `resolve_agent_id()` (local-first, live 8004scan fallback for a numeric miss), `classify_address()` (EOA vs contract via `eth_getCode`, known-contract table, live ERC-20 self-check), `resolve_search_fallback()` (the one real entry point). A real, bounded 5-minute in-process cache (max 5,000 entries, cleared rather than left to grow — same discipline the recent `protocol_compat.py` OOM fix established) — a live lookup at search time, never a permanent one, and never an unbounded one either.
- `GET /api/search/resolve?q=...` (`server.py`) — always 200, always a real, categorized `found`/`reason` shape, never a 404. A genuinely nonexistent id/address is itself a real, useful answer.
- `frontend/src/UniversalSearchFallback.jsx` — shared verbatim by web and mobile. Only ever fires for input that already looks like an id or address (mirrors the backend's own classification client-side, so an ordinary mistyped name never triggers a live network call); a local hit resolves back to the app's own full agent object and opens the real detail view directly; a live-only hit, a wallet, or a contract each get their own honest, clearly-labeled card; a genuinely unrecognized or not-found result gets a plain, real message — never silence.
- Both marketplace search boxes' placeholder text updated to say this is now possible.
